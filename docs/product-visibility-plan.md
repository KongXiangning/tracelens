## 2. 本轮目标、非目标与实施自主权

### 2.1 完成后的用户效果

用户应能从已登记项目进入需求视图，理解目标、模块、需求及设计的明确关系；打开项目规划，看到原有顺序、阶段、未来范围、工作项与任务关联；从某项需求找到多个实施任务及后加修复，反查其覆盖和来源；同时区分明确声明、推断、已否定关联、范围化交付报告及尚未核对的信息。

这些结果必须与原任务、文档和关系页面连通，不能另做一组无法跳回原文的静态卡片。

### 2.2 不做什么

不接 vNext Runtime API，不调用模型，不执行被观察项目中的 helper 或脚本，不重放 journal，不写被观察项目；不新增任务执行、审批、自动排程、完成率推断、语义推断、向量检索、数据库、实时监听、桌面壳或远程协作。保留已有 Codex 项目选择、目录浏览、候选盘点、整理提示词和使用说明页。

文档中已经记录的 `inferred` 可以展示；这不授权 TraceLens 自行运行 AI 推断。明确 SourceRef 或现有 adopted-plan 引用指向单个记录时，可以在既有边界及本方案的来源策略内只读查看；这不等于允许扫描 records 全集。

### 2.3 对 Sol / Astra 的执行方式

两者共用此方案，不建立按模型分叉的协议或两套功能规格。固定目标、来源语义、身份、状态边界、失败行为和验收；函数、局部拆分、组件组织、类型名称及合理的工程调整由实施者决定。

默认由一个 Agent 负责连续实施；另一个 Agent 可在首次贯通标准读取后及最终交付前，审查身份、来源、降级与实际差异。独立复核是建议，不是每一步的强制往返或解锁条件。仅有一个模型时，也按相同验收完成。

不规定“每步最多几个文件”，不要求每个字段对应一个测试，不要求先把所有未来任务建出来。若使用现有 vNext 管理本次工作，按当前真实进度建立 bounded task，不为本方案安装或扩张工作流。

## 4. 技术方案与不可混淆的语义

### 4.1 双通路读取，共用安全边界和一个快照

保留现有 Profile / 通用文档通路；增加 PRODUCT 标准通路。两者共享有界文件读取、路径检查、单次读取缓存、文件预算和快照提交，但分别记录读取范围与解释结果。

PRODUCT 是“标准产品条目”的默认入口，不替代通用文档导航，也不因为某文件被目录引用就把它变成托管条目。反过来，启用 PRODUCT 后，`managed_paths` 中的标准文件不应再受通用导航的三层跳转限制；它们是明确登记输入，但仍受总读取预算和安全规则约束。

标准通路只从所选 manifest 的 `managed_paths` 枚举当前定义。历史、讨论原文和报告按明确 SourceRef 读取，不递归扫描 `source_paths`。即使通用导航读到了历史文件，也只能作为普通材料或来源查看，不进入当前产品条目集合。

不要复用通用导航对坏索引的恢复策略，把旧 PRODUCT 定义混入本次当前结果。有效 manifest 撤回文件后，该文件退出当前定义；manifest 不可用时，产品区明确显示不可用。若发布本次部分成功快照，只发布本次有效内容；若整体刷新失败保留旧快照，整份快照继续标明旧时间和失败，不制造新旧混合的“当前版本”。

### 4.2 配置、预览与兼容

新项目在添加预览中发现 PRODUCT 时展示入口及将读取的范围，用户确认后启用。旧项目配置缺少新选项时不静默扩大范围；给出一次明确的启用入口，确认并手动刷新后生效。允许高级设置指定一个其他 manifest，但一次读取只有一份明确当前入口，不自动合并多个 manifest。

`maintenance: paused` 仍可读。区分未启用、入口不存在、被排除、读取失败、不支持版本、部分可用和有效空结果；不能都退化成零条需求。PRODUCT 未启用不影响旧项目的普通文档、任务和关系功能。

配置变更仍走现有 registry / `configVersion` / `configChanged`；同步修改配置校验、保存、表单及 `App.tsx` 的 `cleanConfig`，避免新字段在保存时被丢弃。不得把产品开启状态与 `autoDiscover` 或 `includeRecords` 混成一个开关。

### 4.3 标准解析：在 TraceLens 内执行，官方解析器作对照

默认实现为 TraceLens 自身受控的标准读取模块，复用已有 Node、TypeScript、YAML 和 Markdown AST 能力，以及固定版本的生产 JSON Schema。可以提取上游真正独立的纯解析逻辑；不得为了复用而引入 Runtime 执行链。

生产环境不执行外部项目的 `.workflow-system/runtime/support/product-maintenance.js`。官方 `offline-reader.mjs` 在隔离夹具上作为测试对照，不作为运行时 shell-out 扫描器；它没有 TraceLens 所需的全部原文、快照和来源核对能力。

优先兼容 v2；v1 按其实际 Schema 只读解释，不静默迁移。未知版本保留原文与诊断。可使用成熟的 JSON Schema 校验依赖并更新锁文件，不自行实现简化版 Schema 引擎，不把整个文档一次校验失败作为隐藏所有条目的理由。

解析必须满足：根级 AST 二级标题与 items 一一对应；正文完整保留到下一根级二级标题；代码、引用、列表里的伪标题不形成条目；严格处理契约规定的 YAML 限制及 UTF-8、BOM、LF / CRLF。产品解析不要直接套用通用 `parseInput` 的全文 heading 收集或状态关键字规则，防止产品正文被误解释为当前任务。

逐项降级以能够安全解析并定位条目为前提。若 frontmatter 整体语法损坏、无法可靠解码，保留整份文件原文与文件级诊断，不信任解析器的残缺对象来拼出“合法条目”。可安全解析的单项 Schema 或章节错误，才按条目隔离，不能借此隐藏同文件的其他可用条目。

一份标准文件允许多类型、多条目，不为了适配 `Document.kind` 拆文件，不要求被观察项目改格式。文件类别仍用于阅读组织，条目 `type` 用于业务语义；二者分开。

### 4.4 在现有 Snapshot 中增加产品视图数据

建议增加一个内存中的 `product` 区域，容纳入口状态、当前可用条目、不可用条目的原文定位、完整元数据、关系、任务绑定、计划工作项、来源核对、诊断和读取覆盖。名称可调整，但不创建新的权威持久化 JSON 协议或中央任务库。

| 概念 | 展示身份与规则 |
|---|---|
| 产品条目 | `(工作副本根, project_id, item_id)`；与 TraceLens 登记 ID 分开；条目 ID 不应用文件路径的大小写折叠规则 |
| 工作项 | 产品命名空间内的 `(plan_id, work_item_id)`，不能仅用工作项 ID |
| TaskBinding | owner 条目 + binding ID，保留完整 task、role、coverage、origin、state、reason、sources、plan_items、repairs |
| 原文位置 | 同一个 `snapshot.id` 内的文件、字节摘要、条目位置和行号范围 |
| SourceRef | 保留文件 / URI / 文字三种原始来源及定位结果，不能强行全部转成已解析的旧 `SourceRef` |
| 产品关系 | 保留 relation、origin、声明状态及来源；目标解析状态另列，不复用旧 RelationState 表达 active / dismissed |

产品关系与旧 `reference / mention` 可以在同一图层展示，但底层类型与语义不能折叠。`state: active` 不代表目标已定位，目标已定位也不证明关联有效。

不要只用官方 `plan_tasks` 或 `reverse_relations` 做业务模型。它们是派生辅助结果；完整元数据才是推断依据、否定关系和修复范围的读取来源。反向索引可以在内存计算，不回写被观察项目。

### 4.5 来源读取与快照一致性

本轮选择明确策略：在刷新中，对已读条目直接引用的本地来源做有界读取与定位，按规范化路径去重，并保留其来源角色；不递归遍历来源文档里的所有外链，不自动抓取 URI。已被登记为当前文档的内容复用同次字节缓存。

新增必要的纯文本来源支持：Markdown、YAML、JSON、TXT。JSON / TXT 只用于明确引用的来源或既有 adopted-plan 链路，不把它们加入全仓库通用扫描，更不执行其内容。不支持的来源类型保留引用和原因。

当前 `readBounded` 的真实路径、无符号链接、字节预算、UTF-8、读取期间变化检查继续有效。PRODUCT 排除与用户显式排除均优先；`capture_paths` 不是读写或目录遍历授权。records 中的来源只允许在标准允许范围内按精确文件引用读取，不由此打开历史递归扫描。

分别展示来源的未读取、未定位、被排除、不可用、相同字节或已变化。文件 SHA-256、需求定义摘要及 Git SHA 不可混用；需求定义摘要沿用 `vnext-requirement-definition/v1` 原算法，关系、绑定和选择入口的排除规则也不能自行简化。

普通切页、详情和来源跳转仅消费快照，不产生隐式扫描或读盘。预算不足未收录的来源显示未读取，并提示用户调整范围后刷新，不为了点击链接临时读最新磁盘。确已收录的原文通过已有快照接口读取；旧 snapshotId 延续 409 行为。产品正文分段展示仍需使用原文件绝对行号，不能把条目局部第 1 行当原文第 1 行。

业务 inventory、托管文件 coverage、来源内容核对和交付报告分开表示。读取字节完整不等于结构全可用，结构全可用不等于业务盘点完成，二者都不证明交付。

## 5. 四项功能的具体交付要求

### 5.1 项目目标、需求与设计

增加“需求”项目入口，集中展示目标 / 模块组织、完整需求清单及条目详情；设计在相关需求详情和关联图中可达，未关联设计也保留可浏览入口。四种 scope 均可查看，筛选必须清楚表明当前筛选范围，不能把当前筛选数量冒充全项目需求总数。

正确使用 `supports`、`part_of`、`addresses` 等声明。它们构成可追溯关系，不保证严格树形；不得把一项需求强制归入唯一目标或设计。保留没有关系的条目，并写“未记录该关联”，不能判定未实现或遗漏。

详情显示完整业务正文、边界、验收、来源及关联。`current` 不是“未完成需求”，已交付需求继续属于当前范围；`retired` 不是已完成。普通 Markdown 引用不升级为实现或验证关系。

### 5.2 总体规划与实际进展

增加“规划”入口，先选择计划，再按 `work_items` 原数组顺序呈现阶段、预期结果、覆盖范围、原定 / 新增 / 未知、纳入 / 延期 / 撤回及明确依赖。stage 是展示分组，不是阶段状态机；分组不能悄悄重排工作项。

多个计划保持独立身份和采用状态。单计划可直接打开，但不宣称它覆盖全项目；多计划没有明确选择时给出选择列表，不按修改时间、文件名或首项猜当前计划。无计划时仍展示完整已知业务范围、既有任务关联及 project 正文中的规划信息，不自动从正文生成待办顺序。

工作项与任务不是永久一对一。零任务、多个任务、同一任务覆盖多个工作项均可展示。没有显式依赖不证明串行，也不证明可以并行；计划依赖不构成执行权限或 Runtime gate。

“已完成部分、进行中部分、未来安排”必须分三个维度交付，而不是合成一个进度状态：

| 用户看到的内容 | 数据依据 |
|---|---|
| 未来安排 / 后续范围 | plan、work_items、scope 及其完整正文 |
| 当前工作 / 任务状态 | 当前快照中可靠匹配的任务文档明确声明，保留来源及冲突 |
| 已报告交付范围 | 被明确选中的 assessment、subject、覆盖文字及报告来源 |

工作项卡片可以并列显示安排状态和关联任务状态，不从其中任一项推出阶段或需求整体完成。没有足够范围化报告，就显示交付未知；不得用“绑定任务已关闭占比”计算项目完成率。

### 5.3 一个需求多个 Task，以及计划外修复

在 goal / requirement 详情读取完整 TaskBinding，并在任务详情反查关联需求、目标、角色、覆盖及计划工作项。角色属于某条关联，不是整个任务的唯一类型。

任务匹配先区分 UI 身份、明确真实 `task_id`、显示编号与来源位置。对已知 current-view 格式和任务元数据提取真实 ID，但不对所有输入猜测。真实 ID 一致且工作副本、来源不矛盾时可以建立导航；无真实 ID 的历史引用只能按明确来源定位，并保持身份未确认。不能因为 `TASK-811` 同名或标题近似就合并。

`Parsed.task` 当前只提供单文件任务 / 当前焦点，不能据此假设所有历史任务已被建模。对实际支持的历史文档可以提取明确任务声明或只定位原文；没有资料的绑定仍可展示，不造虚假任务实体。一个当前文件改换焦点后，即使 UI 文件 ID 不变，也必须重新核对真实身份，防止旧需求关联继续挂到新任务。

同一真实任务在多个来源中出现时保留状态观察的出处；冲突并列显示，不按时间猜胜者。标准中的 `task_id: null` 不回填成 TraceLens UI ID。`step_id` 只表示原任务内步骤，不创建新的 task；项目 `plan_id` 不等于 Runtime `plan_ref`。

E6 场景的预期闭环：原 A / B / C 工作项身份保留；R 作为 added 工作插入；REQ 同时保留 A / B / C / R 的范围绑定；R.role=repair，repairs 指向 A 的相关交付范围；C 没创建时只显示工作项；修复前提按明确声明展示。修复 A 的交付不证明 A 引入缺陷，不将 A 自动重开，也不把 R 关闭当作新 PASS。

### 5.4 明确记录、推断、报告与未知

关系同时保留 `origin: declared / inferred` 与 `state: active / dismissed`。推荐标签“明确声明 / 推断关联 / 已否定关联”，不把 declared 翻译成“已证实事实”。推断依据、理由和来源可打开；已否定关系可以默认不进主图，但必须有可发现的查看入口和理由，不能在数据层丢弃。

assessment 只沿 requirement.assessment_id 选择。未选择、目标不匹配、引用无效分别提示；不得自动选最新一条。implementation、verification、subject、checked_at、覆盖范围、定义对齐和 pending_sources 同时显示；没有旧原件则历史可核验性未知，摘要相同也不证明当前代码仍适用。

旧局部 pass-reported 与新反馈 pending_sources 同时可见，不能在总览只露出一个绿色通过标记。不同对象或不同范围的报告不机械合成一个全局 mixed。讨论可以展示原文、整理摘要、未决问题和 discusses 关联，但“有关联”不等于“已采纳”。change 展示变化范围、依据与未同步项，不假装记录变更即证明所有正文已经同步。

`pages.tsx`、`App.tsx` 已承载现有页面；新业务可合理拆出组件，但不要以本轮为由全量重构。使用说明只需补与新功能直接相关的阅读指引、维护入口和版本说明，不在本轮泛化成全套技能文档同步项目。

## 7. 状态和错误处理约定

| 情形 | 应显示 / 应执行 |
|---|---|
| 没有 PRODUCT 或产品读取未启用 | 区分“未发现入口 / 未启用”，旧功能继续工作 |
| maintenance paused | 允许读取，明确维护暂停不是项目结束 |
| 一份文件混合九类条目 | 按条目类型显示，原文件只保存一份快照内容 |
| 单个坏条目 | 保留其他可用条目及坏项原文位置，不静默剔除 |
| 重复当前 ID | 冲突条目不能参与无歧义连接，保留冲突来源，不取最新文件获胜 |
| manifest 已撤回条目 | 退出当前定义；仍被明确引用的内容可作为来源，而非当前条目 |
| manifest 坏掉 / 不支持版本 | 产品区显示失败或不支持及原文，不显示“当前无需求” |
| source 不在有效范围 / 不可读 / 预算耗尽 | 原引用和具体原因保留，不伪造定位、摘要或完成 |
| 整体刷新失败 | 沿用旧快照并标示旧时间，不发布新旧混合数据 |
| 刷新后选择的条目已移动 / 删除 | 同 ID 在新位置重新定位；已退出本次范围则明确失效，不跳到同名条目 |
| 两个 worktree project_id 相同 | 按工作副本隔离，不合并未提交内容 |
| 只有历史任务显示编号 | 保留历史原文及身份未知，不用编号猜真 ID |
| 当前焦点存在但任务状态未记录 | 可显示焦点，状态仍未记录；聚焦不等于正在执行 |
| 旧报告通过且有新反证 | 并列显示旧范围、未知适用性和待对账，不升级为当前完整通过 |

数据层校验和界面展示应共用相同诊断对象或映射；诊断可以分级，不能为了把刷新状态刷成成功而删掉未核对材料。读取、结构、关联、业务盘点、交付五类结果不应塞进一个含混的 success 布尔值。

## 8. 三个实施批次

这些是可验收范围，不是必须逐函数照抄的流水线。安全、来源和未知处理从第一批开始，不留到最后补。

### 批次一：标准条目与目标—需求—设计闭环

同步修订现有需求和架构，明确产品阅读范围；接入固定契约 / Schema / 样例；完成 PRODUCT 预览与启用、标准条目解析、混合文件原文、逐项诊断、同快照索引。增加“需求”入口和相关关系导航，使目标、模块、需求、设计可以互查并回到原文。

本批最小可见结果是：用户添加或启用综合样例后，能浏览九类条目中的可用内容，按四种需求 scope 过滤，打开目标—需求—设计关系，查看完整正文及来源；坏条目不消失，旧 Alpha / Beta / Gamma 项目仍能按旧方式使用。其余类型可先以完整详情呈现，不能因为专用面板尚未完成而丢数据。

完成本批后审查一次双通路范围、身份与原文定位。无需为组件命名、函数拆分或普通局部修复另行请求批准。

### 批次二：总体规划、任务身份与修复可追溯

完成“规划”入口、单 / 多 / 无计划呈现、原顺序与 stage、工作项覆盖与依赖。补真实 task_id 提取、受约束的历史来源匹配、TaskBinding 正反向展示及 repairs 细节；让任务页、需求页、规划页和局部图形成闭环。

本批验收用 E6 和规划消费样例：一个需求多个工作项 / 多个任务；C 未创建；R 后加入并指向 A 的范围；无计划仍可浏览完整需求；同名工作项处于不同 plan 不相互串线；无显式依赖不擅自判断并行；当前任务步骤与 adopted-plan 来源跳转保持原行为。展示文档状态，不添加 Runtime 查询。

### 批次三：交付报告、推断来源与整体交付

完善 assessment 入口、原范围 / 对象 / 版本、定义摘要核对、pending_sources、change 与 discussion。补齐总览的规划 / 当前工作 / 报告分区、已否定关系入口、来源原文和失败说明；完成所有页面的跨入口导航及新旧功能回归。

执行完整检查与生产浏览器验收，更新 README 和支持范围说明，记录实际结果与限制。真实样本可用时做只读核对；没有可用样本时以明确标注的合成样例完成已有范围，不能宣称真实项目或全版本兼容。最后按本方案的用户闭环复核实际差异，而不是只审类型和测试数量。

## 9. 验证方案

### 9.1 复用而非重建

沿用 Vitest、已有服务测试及生产浏览器启动方式。按职责新增少量产品解析 / 索引测试及浏览器场景即可；可以拆分已有过长测试文件，不要求一个风险一份新测试文件。纯展示文案不逐条建测试，关键业务解释必须有能复核的行为检查。

| 组合场景 | 必须验证的结果 |
|---|---|
| 标准综合样例 | 12 个可用条目、9 类 type、四种 scope；未知任务身份、定义未知和待核对反馈保留；样例数字只用于此夹具 |
| AST / YAML / Schema | BOM / CRLF；代码、列表与引用中的伪标题；非法 YAML / 单坏条目 / 重复 ID / 不支持版本正确降级，完整正文与行号一致 |
| 无计划与多计划 | 不隐藏已知需求；显式选择、原顺序、跨阶段覆盖；同名工作项不串 plan；共享约束无直接绑定不报未实现 |
| E6 插入修复 | 原 A / B / C 保留；R=added、repair、范围化 repairs；C 无 Task 不造 ID；任务内部步骤不拆成独立任务 |
| 真实任务身份 | TASK 显示编号与真实 ID 分离；null、冲突、多个来源；同一 CURRENT_TASK 文件焦点改变后旧绑定不误挂新任务 |
| 新旧材料并存 | 旧 pass、当前适用性未知、新反馈待对账；assessment 未选择或目标错配；原文相同不自动清掉待核对 |
| 来源与范围 | history / raw 不作当前定义；精确 TXT / JSON 来源可读；URI 不自动抓取；排除、越界、链接、不可读和预算中断保留原因 |
| 刷新与身份 | 新增、移动、修改、删除、撤回 managed 登记、manifest 损坏；无隐式扫描；旧快照 ID 失效；新旧内容不混用 |
| 现有能力回归 | Codex / 目录选择、通用导航与候选、records 开关、当前任务计划跳转、原文与旧关系、静态指南继续可用 |
| 生产浏览器闭环 | 添加 / 启用→需求→设计 / 原文→规划→任务→修复→报告待核对→修改夹具→刷新；长标题、中文路径、窄屏及错误状态可用 |

官方离线解析器对照应比较可比较的条目、类型、正文、定义摘要、关系、工作项顺序和诊断解释；不比较随机 ID、绝对工作目录或读取时间。TraceLens 本轮增加的来源核对单独验证，不因官方离线输出未读取来源而删除自己的来源检查，也不要求两种 envelope 逐字相同。

原始字节摘要与定义摘要的测试必须用实际文件 / 契约算法，不能填全零值冒充验证。对被观察样例或授权只读副本，核对运行前后内容未被工具修改。允许测试脚本修改隔离夹具来测试刷新；不修改外部实际项目来迁就解析器。

### 9.2 实际命令与证据

依 `package.json`，当前 Node 要求是 `>=22.12.0`，使用 npm 与现有锁文件。开始实施时核对实际版本和脚本；不要为了沿用本方案命令而回退新基线。

```sh
npm ci
npm run check
npm run format:check
npm run test:browser
```

`check` 已包含类型检查、测试与构建；无需再把同一轮重复运行的 typecheck / build 算成独立验收。开发中先跑受影响的定向测试，完整命令在集成后运行。`test:browser` 使用构建后的生产服务，运行前确保 build 成功及所需浏览器可用。

`npm run test:real` 依赖实际可用样本和脚本输入，先阅读脚本，不默认存在原作者机器路径；必要时为已有脚本加可选显式样本参数。没有授权或样本则如实记录未运行，不制造真实数据结果。

优先核对 Windows 原生、中文和空格路径；其他操作系统上运行成功不能代替 Windows 实测。浏览器可沿用 1440 / 1024 / 390 宽度检查关键布局，不要求每页每组合都截屏。环境阻塞保留失败日志和未验证项，不通过删除场景把结果改写为全部通过。

## 10. 最终完成定义与交付报告

本轮完成要求四项用户目标都具备真实功能，并贯通原有项目选择、文档、任务和关系功能。能够展示可信的未知，比伪造完整状态重要；但“所有内容都显示未知”不能代替已经有明确依据的匹配和展示实现。

交付可运行代码、必要依赖锁文件变更、固定来源资产、最小样例、相关测试、更新后的现有需求 / 架构与 README。文档应明确支持的版本、字段 / 格式、读取边界、手动启用、来源策略、已验证环境及未验证项。

最终报告只需写明：实际起止提交和改动范围；三个批次的用户效果；运行命令与结果；少量关键浏览器证据；未完成 / 未运行 / 已知限制；是否改动外部文件，以及当前 Git 状态。对继承的基线问题和本轮引入的问题分别说明；没有实际复现的风险不冒称已确认故障。

不以测试条数、通过率、生成文件数或截图数量宣布产品完成；不要求为每条文字建立测试。没有运行测试就写未运行，没有验证页面就不能写端到端通过。

## 11. 实施中的最小决策规则

本轮允许新增少量本地产品模块、必要的 Schema 校验依赖、类型、页面、夹具，以及与接入直接相关的配置与安全读取调整；不需要因为涉及多个模块就另起重构项目。

遇到旧 v0.6 文档中“一律不读 records / 只读 Markdown、YAML”与实际 adopted-plan 行为或新来源需求的表面冲突，在现有需求和架构中明确本轮有界扩展：不读 journal 状态链，不执行脚本；只按当前任务或产品材料明确引用读取必要 JSON / TXT。不得通过忽略已有测试或扩大成任意文件读取来消解冲突。

只有改变用户目标、引入外部写入 / 执行、联网获取私人正文、新增持久化业务真相或自动判定完成等范围变化，才属于需要重新取得决定的事项。普通工程选择在本轮范围内解决。资料不完整不必阻塞所有开发；在不捏造数据的前提下交付可用部分并标明缺口。
